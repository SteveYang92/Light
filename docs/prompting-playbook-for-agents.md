# Prompt Engineering — 核心方法论

基于 Anthropic Margot Van Laar 演讲《The Prompting Playbook》总结，用于指导 Agent 提示词设计与调试。

---

## 一、评估先行：一切改动的基础

**在动提示词之前，必须先有 eval suite。** 没有评估，你无法判断改动是否真正带来性能提升。

### Eval 用例应覆盖三类：

| 类型 | 描述 |
|---|---|
| **对照用例 (Control)** | 模型擅长的、无歧义的问题，应永远通过 |
| **边缘用例 (Edge cases)** | 曾让模型失败的场景，确保历史错误不会重演 |
| **能力边界 (Boundary)** | 模型应清楚何时转人工、何时直接拒绝 |

---

## 二、提示词通用卫生 (General Hygiene)

在针对具体失败模式之前，先做基础清理，这往往能带来**立刻的提升**。

### 2.1 结构化管理

- 用 **XML 标签** 分隔不同关注点：`<role>`、`<policy>`、`<guidelines>`、`<tone>`、`<data>`
- 不要把指令、策略、语气、数据混在一个大段落里

### 2.2 经验法则

> 如果你读提示词时分不清 guidelines、policy 和 data，模型大概率也分不清。

### 2.3 清理清单

- 删掉说"你是人类"之类的虚假角色描述
- 删除从网页直接复制过来的无关内容（hero image、cookies 等）
- 移除针对**旧模型行为的补丁**——它们可能在新模型上导致过拟合
- 不要让多人在无归属的情况下积累补丁，**提示词应有明确 owner**

### 2.4 输出契约 (Output Contract)

- 在提示词中明确定义输出格式（XML 标签、JSON schema）
- 在 API 调用层设置 **stop sequence**，确保生成在预期位置停止
- 对于复杂输出结构（嵌套 JSON），使用 **structured outputs** 功能

---

## 三、核心原则：指令不能增加能力

**Telling the model to "do a good job" doesn't make it better at math.**

- 告诉模型"必须正确计算" → 无用
- 给模型一个**工具**来完成计算 → 解决
- 告诉模型"不要含糊其辞" → 无用
- 提供明确的计算公式/逻辑 → 解决

### 实践模式：

```
推理 → 用 LLM
执行 → 用工具 (tool use)
```

---

## 四、避免过拟合：模型在优化你的目标

### 4.1 信息隐瞒 (Information Withholding)

- 问题：`"永远不要给客户错误的套餐信息，引导他们去查 URL"`
- 结果：模型有数据也不提供，过度保守
- 修复：`"你的客户数据是准确的真值来源，给出平衡的观点"`

**模型不仅会编造事实（hallucination），也会隐瞒已有信息。**

### 4.2 给出权衡的两面

- 问题：`"避免升级到人工，除非绝对必要，因为一次升级成本 $8"`
- 结果：模型几乎从不升级，死撑着自己解决
- 修复：`"升级成本 $8，但如果搞错了，会导致退款和失去客户信任"`

**只给单面信息 → 模型过度优化到一端。给两面 → 模型自己做出权衡。**

### 4.3 补丁管理

- 旧模型迁移补丁可能变成新模型的**过拟合来源**
- 使用**版本控制**管理提示词，记录每个修改的原因
- 旧补丁在适当时候应删除，而非无休止积累

## 五、三个可调节的杠杆

构建 Agent 时，不只靠提示词：

| 杠杆 | 说明 |
|---|---|
| **提示词 (Prompt)** | 结构、指令、示例 |
| **模型 (Model)** | 推理能力、遵循指令能力、速度 / 成本 |
| **框架 (Harness)** | API 参数（max_tokens, stop, thinking budget）、工具定义、多轮循环 |

### 模型选型策略：

1. 先用**小模型 + 简单提示词**建立基线
2. 换大模型（不改提示词）→ 观察推理能力带来的提升
3. 用增强推理（adaptive thinking / extended thinking）→ 观察 token/延迟换取质量
4. 如果大模型成本太高，回到小模型 **+ 优化提示词**

## 六、Agent 架构：生成-评估-修复循环

对于复杂任务，**不要用一个巨型提示词解决一切**。拆分成三个独立提示词：

```
[Generator] → 初稿生成
     ↓
[Evaluator] → 逐条检查违规，返回证据
     ↓
[Repairer]  → 针对性修复违规项
```

### 优势：

- 每个提示词简单、独立、可单独调试/评估
- 比单一大提示词 **更省 token、延迟更低**
- 可在运行时注入**软约束**（无需改后端代码）：
  - 例：「Harry 不喜欢和 Sally 一起工作，尽量分开」
  - 例：「周三需要第三个班次」

---

## 七、日常工作流总结

### 维护已有提示词：

1. 建好 eval suite（对照 + 边缘 + 边界）
2. 跑基线 → 识别失败模式
3. 先做通用卫生清理（结构、冗余删除、输出格式）
4. 逐条针对失败模式修复（不一次改太多）
5. 每次改动后跑 eval 验证
6. 用版本控制记录改动原因

### 从零构建新 Agent：

1. 定义清晰的任务约束和 eval 方案
2. 从简单提示词 + 合适模型开始
3. 如果不行，先换模型 → 再换提示词策略 → 再改框架
4. 复杂任务考虑拆分为 generate-evaluate-repair 循环
5. 持续优化 cost/latency/quality 三角

---

## 八、禁忌清单

- 不要用 "you are a helpful AI" 这种模糊的角色描述
- 不要堆积"禁止做 X"的黑名单 —— 容易过拟合
- 不要告诉模型"必须做对"而不给做对的**能力或工具**
- 不要把 web 原始内容原封不动塞进 system prompt
- 不要无人负责地多人合写提示词
- 不要把 policy、tone、data、instructions 混在一个大段落
